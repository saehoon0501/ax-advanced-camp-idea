Reasoning Model vs 기존모델
Reasoning Model(Claude의 Extended Thinking, OpenAI의 o1 등)은 기존 모델과 근본적으로 다른 방식으로 작동합니다.

기존 모델: A → Z 직행
기존 모델은 입력(A)을 받으면 한 번의 forward pass로 바로 출력(Z)을 생성합니다:





입력: "1293 × 847 = ?"
      │
      ▼ (한 번의 추론)
출력: "1095171"  ← 틀릴 수 있음


모델의 "깊이(depth)"가 고정되어 있기 때문에, 복잡한 문제는 한 번에 풀기 어렵습니다.



Reasoning 모델: A → B → C → D → ... → Z
Reasoning 모델은 중간 단계를 명시적으로 열거합니다.



입력: "1293 × 847 = ?"
      │
      ▼ (Extended Thinking)

[내부 사고 과정]
B: "1293 × 847을 분해하자"
C: "1293 × 800 = 1,034,400"
D: "1293 × 47 = ?"
E: "1293 × 40 = 51,720"
F: "1293 × 7 = 9,051"
G: "51,720 + 9,051 = 60,771"
H: "1,034,400 + 60,771 = 1,095,171"
      │
      ▼
출력: "1,095,171"  ← 정확함


핵심 의의: Depth 한계 극복
LLM은 통계적 패턴 매칭 기반입니다. 모델 파라미터(가중치)가 고정되면, 한 번의 forward pass로 수행할 수 있는 "추론의 깊이"도 제한됩니다.

Reasoning 모델은 이 한계를 Inference Time Compute로 극복합니다.

추론 방식	입력 → 출력 (1단계)	입력 → 중간 단계들 → 출력
복잡한 문제	깊이 부족으로 실패	단계를 나눠서 해결
비용	고정	문제 복잡도에 비례
비유	암산	종이에 풀이 과정 작성
비유: 암기력이 좋은 사람도 복잡한 계산은 머릿속으로만 하기 어렵습니다. 종이에 중간 과정을 적으면 훨씬 복잡한 문제도 풀 수 있습니다. Reasoning 모델은 "종이에 적는" 과정을 모델 내부에서 수행합니다.



Chain-of-Thought (CoT) 부스팅
기존 모델에서의 CoT
기존 모델에서는 명시적으로 "단계별로 생각해보세요"라고 요청해야 했습니다:



# CoT 없이
prompt = "1293 × 847은?"
# → 모델이 바로 답 시도 (오류 가능성 높음)

# CoT 적용
prompt = "1293 × 847은? 단계별로 계산 과정을 보여주세요."
예시:
    # 단계별로 계산 과정을 예시로 작성
# → 모델이 중간 과정을 출력하면서 정확도 상승


Reasoning 모델에서는?
Reasoning 모델은 내부적으로 CoT를 수행합니다.

단순 질문	명시적 CoT 불필요(모델이 알아서 판단)
특정 형식 원할 때	"과정을 보여달라"고 요청
디버깅/검증	사고 과정 출력 요청하여 확인




# Reasoning 모델에서 불필요한 프롬프트
prompt = "단계별로 생각해서 답해주세요: 1+1은?"  # 오버킬

# 효율적인 프롬프트
prompt = "1293 × 847은?"  # 모델이 필요시 내부적으로 CoT 수행


언제 명시적 CoT가 여전히 유용한가?
출력 형식 지정: "풀이 과정을 마크다운으로 보여줘"

교육 목적: 사용자에게 과정을 설명해야 할 때

검증 필요: 모델의 추론 과정을 확인하고 싶을 때

특정 방법론 강제: "귀납법으로 증명해줘" or 원하는 수행 절차 강제(phase 1, phase 2, ...)


프롬프트가 모델 내부 전문성을 활성화하는 원리
최신 대형 LLM들은 내부적으로 여러 "전문가(Expert)" 네트워크를 가지고 있으며, 입력에 따라 적합한 전문가가 활성화됩니다 (Mixture of Experts 아키텍처). 중요한 것은 **프롬프트의 내용과 스타일이 어떤 전문가가 활성화되는지에 직접 영향을 준다**는 점입니다:

"def function():"	코딩 관련 Expert
"∫ x² dx" 포함

수학 관련 Expert
"번역해줘"	다국어 Expert
법률 용어 다수	법률/전문 분야 Expert
Tip) 프롬프트 작성 시, 맨 처음 페르소나 작성을 통해 원하는 Expert를 더 확실히 강조할 수 있습니다. 예: "너는 20년차 시니어 Python 개발자야"

실습 연결: Dynamic Prompt 실습에서의 적용

이 섹션에서 배운 원칙을 **Dynamic Prompt 실습**에서 직접 적용합니다:

| 이론 | 실습에서의 적용 |
|------|---------------|
| **Expert Activation** (역할 부여) | `CODING_AGENT_SYSTEM_PROMPT`에서 "당신은 Coding Agent입니다" → 코딩 전문가 활성화 |
| **일관된 도메인 언어** | Static prompt에 코딩 용어와 Phase 구조를 일관되게 사용 → 동일 Expert 유지 |
| **Prompt Caching** (Section 1 연결) | Static 부분(역할 + 규칙)을 prefix로 고정 → 캐시 재사용으로 비용/지연 절감 |
| **Dynamic 주입** | 런타임 상태(workspace, todos)는 suffix로 추가 → 캐시를 깨지 않으면서 최신 컨텍스트 반영 |

핵심: Static prompt의 persona 정의는 단순한 역할극이 아닙니다 — 모델 내부의 적합한 전문가를 활성화하는 **기술적 선택**입니다.
