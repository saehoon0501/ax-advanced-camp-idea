## Agent Harness란 무엇인가

Agent Harness는 LLM을 감싸는 **제어 계층(control layer)** 입니다. Stateless인 모델을 도구를 사용하고, 스스로 수정하며, 여러 세션에 걸쳐 작동하는 프로덕션 에이전트로 변환하는 모든 코드, 설정, 실행 로직을 의미합니다.

공식적으로는 **Agent = Model + Harness** 로 정의됩니다.

```
┌─ Harness ─────────────────────────────────┐
│                                            │
│  System Prompt    ← 역할과 규칙            │
│  Tools            ← 행동 수단              │
│  Middleware        ← Context Engineering    │
│  Orchestration     ← 흐름 제어             │
│  State Management  ← 상태 영속성           │
│  Permissions       ← 안전 경계             │
│                                            │
│         ┌─────────┐                        │
│         │  Model  │  ← LLM (stateless)     │
│         └─────────┘                        │
│                                            │
└────────────────────────────────────────────┘
```

비유하자면, 말(Horse)은 혼자서도 강력하지만 농사에는 쓸 수 없습니다. **마구(Harness)** 가 말의 힘을 유용한 작업으로 방향을 잡아줍니다. LLM도 마찬가지입니다 — 모델은 강력하지만, harness 없이는 프로덕션에서 신뢰할 수 없습니다.

## 왜 모델이 아니라 Harness가 중요한가

직관적으로는 "더 좋은 모델 = 더 좋은 결과"라고 생각합니다. 하지만 실증 데이터가 이를 뒤집습니다:

| 사례 | 모델 변경 | Harness 변경 | 결과 |
|------|----------|-------------|------|
| LangChain (Terminal Bench 2.0) | 동일 | Harness만 개선 | Top 30 밖 → **Top 5** |
| Anthropic 장기 실행 에이전트 | 동일 | 검증 루프 추가 | 83% → **96%** task 완료율 |

같은 모델 가중치로, **harness만 바꿔서** 이 정도의 차이가 발생합니다.

왜 그런가? LLM이 채울 수 없는 6가지 근본적 gap 때문입니다:

| LLM의 한계 | Harness가 제공하는 것 |
|-----------|---------------------|
| Stateless (상태 없음) | 상태 영속성 (Checkpointer, 파일) |
| 텍스트만 생성 | Tool calling, 코드 실행 |
| 유한한 context window | Compaction, 요약, RAG |
| 자기 평가 불가 | 외부 검증 (E2E 테스트) |
| 안전 경계 없음 | Permission, Guardrail |
| 세션 간 연결 불가 | Git, progress 파일, init script |

> **핵심**: 프로덕션 에이전트의 품질은 모델 지능이 아니라 인프라(harness)가 결정합니다.


## Anthropic의 목표: Context를 넘어 Harness로

목표: Claude 기반 코딩 에이전트를 통해, 여러 번의 실행과 많은 Context window에 걸쳐서 웹 애플리케이션을 점진적으로 구현·개선하여, 미리 정해진 기능 목록을 실제로 만족하고 브라우저에서 끝까지 동작하는 상태에 도달하는 것입니다.

좀 더 풀어서 말하면, 에이전트는 다음을 목표로 합니다.

단순히 "코드를 좀 쓰는 것"이 아니라, 사전에 정의된 기능 목록의 각 항목을 실제로 동작할 때까지 구현하고, 그때에만 완료로 표시하는 것.

레포지토리(파일, git 히스토리), 테스트, 진행 로그, 브라우저 확인 등을 활용해 여러 번의 실행에 걸쳐 앱을 반복적으로 디버깅하고 개선하는 것.

이후 실행될 다른 에이전트나 사람이 "어디까지 되었고, 무엇이 깨져 있고, 다음에 무엇을 해야 하는지"를 명확히 이해할 수 있도록, 프로젝트를 장기 개발에 적합한 상태로 남겨두는 것

### 직면한 문제들

LLM은 stateless 기반이기에, 상태 정보를 보존하지 않습니다. 따라서, 세션이 끊기면 모델은 이전 작업의 맥락을 전혀 알 수 없습니다.
이때 에이전트는 이전까지 작업 상태를 알 수 없기 때문에 스스로 그 상태를 추론하거나 상상하려고 시도하고 그 추론이 점점 누적되면서 작업이 틀어집니다.

실제 장기 실행 시나리오에서는 다음과 같은 치명적인 Agent 실행 패턴이 반복됩니다.

한 번에 너무 많은 것을 시도하는 경우 (one-shotting)
 → context 중간에 기능이 반만 구현되고 끊긴다. 다음 세션은 이 깨진 상태를 해석하느라 시간을 허비합니다.

이미 구현된 기능을 다시 구현하는 경우
 → "이게 끝났는지 아닌지"를 판단할 근거가 없음

전체 작업이 끝났다고 잘못 판단하고 종료하는 경우
 → 명시적인 완료 조건이 없음


Q. 그런데 Claude Agent SDK에는 compaction(누적된 내용을 요약하여 context window 공간 확보)이 있는데, 왜 이걸로는 충분하지 않나요?
A. Claude Agent SDK는 compaction 기능 덕분에 한 세션 안에서 상당히 오래 작업을 이어갈 수 있지만, 여러 세션에 걸친 장기 프로젝트를 "안정적으로" 이어가기에는 부족합니다.
    compaction은 대화를 요약해 다음 컨텍스트에 넘겨줄 수 있지만, 중요한 구현 의도나 중간 상태가 요약 과정에서 사라지거나 애매하게 남으면서, 다음 세션의 에이전트가 "이 코드베이스가 지금 어떤 상태인지"를 추측해야 하는 상황이 자주 발생합니다.



## Anthropic의 문제 해결

Anthropic에서는 먼저 문제를 두 부분으로 나눴습니다.

초기 환경 세팅: 첫 세션에서, 이후의 모든 기능 구현을 위한 뼈대를 갖춘 환경을 세팅. → Initializer agent

매 세션마다 점진적(Progressive) 작업: 이후의 코딩 에이전트는 매 세션마다 "한 번에 너무 많은 것을 하려 하기보다, 한두 개의 기능에 집중해 점진적 개발을 진행,
세션을 마칠 때마다 상태를 깨끗하게 정리해서 남긴다. → Coding agent

### Harness 고안

정의: 단일 context나 에이전트를 넘어, 에이전트가 여러 context window와 세션에 걸쳐 일관되게 작업하고 상태를 인수인계하도록 강제하는 전체적인 실행/환경 관리 프레임워크

구체적으로는 다음과 같은 "외부 구조" 전체를 포함합니다.

initializer agent와 coding agent라는 두 종류의 프롬프트 구성
init.sh
claude-progress.txt
git 히스토리 및 커밋 내용
구조화된 feature 리스트(json)
브라우저 자동화 테스트 도구 등

이를 통해 각 세션이 모델의 기억에 기대지 않고 외부 상태를 읽음으로써 "지금 무엇을 해야 하고, 무엇을 남기고 끝내야 하는지"를 자연스럽게 따르게 됩니다.

```
┌─ Harness 구성 요소 ──────────────────────────────────────┐
│                                                           │
│  Prompt 구성          init.sh              Git 히스토리    │
│  (Initializer/Coding)  (세션 복구 스크립트)   (상태 기록)    │
│                                                           │
│  feature_list.json    progress.md          E2E 테스트      │
│  (작업 목록)           (세션 로그)           (완료 검증)     │
│                                                           │
│              ↓ 이 모든 것이 합쳐져서 ↓                     │
│                                                           │
│     에이전트가 "기억"이 아닌 "읽기"로 상태를 파악           │
└───────────────────────────────────────────────────────────┘
```



## 핵심 아이디어: 암묵적 기억 → 명시적 상태

Anthropic의 핵심 해결책은 context를 모델 내부의 암묵적 기억에서, 파일·리포지토리·테스트 결과로 구성된 명시적 상태(explicit state)로 전환하는 것이었습니다.
context를 단순히 요약(compaction)해서 다음 세션으로 넘겨주는 대신, 파일 시스템과 git, 테스트 결과에 "현재 상태"를 기록해 두고, 에이전트는 매 세션마다 이를 읽어 해석하도록 설계한 것입니다.

이 전략은 크게 네 가지 Context Engineering 요소로 나뉩니다.



### 1. Context의 외부화 (Externalization of Context)

첫 번째 요소는 context를 모델 내부가 아니라 외부 아티팩트로 이동시키는 것입니다.

Initializer Agent는 초기 세션에서 다음을 수행합니다.

전체 요구사항을 구조화된 feature list로 정의하고, 각 기능에 대해 passes: false로 초기화

각 기능의 완료 여부를 명확한 boolean 상태로 관리

이전 작업 내역과 의사결정을 claude-progress.txt 같은 진행 로그로 기록

실행 가능한 초기 코드 상태를 git으로 고정

이로 인해 context는 더 이상 "대화 속에 흩어진 정보"가 아니라, 파일 시스템과 리포지토리에 존재하는 상태가 됩니다.
에이전트는 기억할 필요 없이 읽기만 하면 됩니다.

### 2. 컨텍스트 해석 프로토콜 ("Getting Up to Speed")

두 번째 요소는 에이전트가 상태를 해석하는 과정을 시스템적으로 강제한 것입니다.

모델이 스스로 "무엇을 했더라?"라고 추론하게 두는 대신, 모든 Coding Agent는 세션 시작 시 다음과 같은 4단계 프로토콜을 반드시 수행합니다.

1. pwd 및 ls로 현재 작업 디렉토리 확인
2. git log와 진행 로그 파일을 읽어 과거 이력 파악
3. features.json을 읽어 우선순위가 높은 미완료 기능("passes": false) 하나를 선택
4. init.sh를 실행하여 개발 서버를 띄우고 기본 상태 점검

이 프로토콜은 모델의 "창의성"이 개입할 여지를 없애고, 모든 세션이 동일한 관찰 절차를 거쳐 같은 전제 위에서 판단하게 만들어 줍니다.

### 3. 안전망으로서의 Git과 작업 단위 격리

세 번째 요소는 에이전트의 실수를 전제로 한 복구 메커니즘입니다.

**Git Revert 활용:** git commit은 단순한 기록용이 아닙니다. 에이전트가 코드를 망가뜨렸을 때,
즉시 이전의 작동하는 상태(Working State)로 되돌리는 안전장치입니다. 에이전트 스스로 git checkout을 통해 실수를 되돌릴 수 있게 했습니다.

**작업 단위 제한:** Coding 에이전트에게 한 번에 하나의 기능만 처리하도록 강제했습니다.
이는 컨텍스트가 복잡해지는 것을 막고, 각 단계가 독립적으로 검증 가능하게 만듭니다.

### 4. 엔드투엔드 테스팅 강제 (End-to-End Testing Enforcement)

마지막으로 가장 중요한 요소는, "완료"의 정의를 모델의 판단이 아닌 실제 E2E 테스트 통과 여부로 고정하는 것입니다.

실제 브라우저를 띄워 페이지를 로드하고, 버튼 클릭, 폼 입력 등 사용자 시나리오를 실행
기대되는 UI/동작이 실제로 나타나는지 확인

이 테스트를 통과해야만 features.json의 해당 항목을 passes: true로 변경할 수 있습니다.
그 결과, "구현했다고 생각함"과 "실제로 end-to-end로 동작함" 사이의 간극이 기술적으로 차단되고, 에이전트가 너무 일찍 승리를 선언하는 실패 패턴을 줄일 수 있습니다.


## Compound Reliability — 왜 하나씩만 해야 하는가

Anthropic이 "한 번에 하나의 기능만"을 강제하는 것은 단순한 경험 법칙이 아니라, 수학적 근거가 있습니다.

각 step의 성공률이 95%라고 가정합니다. 충분히 높아 보입니다.
하지만 10개 step을 **순차적으로** 실행하면:

```
전체 성공률 = 0.95^10 = 59.9%
```

| 순차 Step 수 | 전체 성공률 (step당 95%) |
|-------------|------------------------|
| 1 | 95.0% |
| 3 | 85.7% |
| 5 | 77.4% |
| 10 | **59.9%** |
| 20 | **35.8%** |

이것이 **Compound Reliability Problem**입니다. Google DeepMind의 2025년 연구에서 180개 설정을 테스트한 결과, 비구조화된 multi-agent 네트워크는 단일 에이전트 대비 오류를 **최대 17.2배** 증폭시켰습니다.

Anthropic의 "하나의 기능만" 규칙은 이 문제에 대한 직접적 대응입니다:

```
한 세션에 기능 5개 시도  → 0.95^50 steps ≈ 실패 확실
한 세션에 기능 1개 집중  → 0.95^5 steps  = 77.4% 성공
                        + git revert 안전망
                        + 다음 세션에서 재시도 가능
```

작업 단위를 작게 유지하면:
- 각 세션의 성공 확률이 높아지고
- 실패해도 git revert로 복구 가능하고
- 다음 세션에서 깨끗한 상태로 재시도할 수 있습니다

> **핵심**: Harness가 작업 단위를 격리하는 이유는 "모범 사례"가 아니라, compound reliability를 제어하기 위한 **엔지니어링적 필수 조건**입니다.
