AI 에이전트는 사용자 대신 코드를 작성하고, 파일을 수정하고 명령어를 실행합니다. 이 과정에서 한 가지 근본적인 질문이 등장합니다.

AI가 잘못된 판단을 하면 어떻게 막을 것인가?

전통적인 소프트웨어에서는 'if-else'문 하나로 권한을 통제할 수 있었습니다. 하지만 AI 에이전트는 자연어를 해석하고 스스로 도구를 선택하는
자율적 시스템입니다. 기존 방식으로는 모든 상황에 대처할 수 없습니다.
이 문제를 해결하기 위해 등장한 방법이 Two-Layer Permission System 입니다.

이 글에서는 이 시스템의 핵심인 Soft Rules와 Hard Rules 개념을 살펴봅니다.



전체 아키텍처
AI 에이전트의 행동을 두 개의 독립적인 레이어로 통제합니다.



┌──────────────────────────────────────────────────────────────────┐
│                        사용자 요청                                │
│                  "테스트 파일 전부 삭제해줘"                         │
└──────────────────────────────────────────────────────────────────┘
                             │
                             ▼
┌──────────────────────────────────────────────────────────────────┐
│                   Layer 1: Soft Rules                             │
│                  (프롬프트 기반 지침)                                │
│  ┌────────────────────────────────────────────────────────────┐  │
│  │ • 요청을 해석하고 적절한 도구를 선택                           │  │
│  │ • 시스템 프롬프트의 가이드라인을 따름                           │  │
│  │ • "파일 삭제 전 확인을 받아라" → 자발적으로 준수                 │  │
│  └────────────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────────┘
                             │
                             ▼  도구 호출 요청
┌──────────────────────────────────────────────────────────────────┐
│                   Layer 2: Hard Rules                             │
│                  (코드로 강제되는 제약)                              │
│  ┌────────────────────────────────────────────────────────────┐  │
│  │ • 위험한 명령어 차단 (rm -rf / 등)                           │  │
│  │ • 워크스페이스 밖 파일 쓰기 시 사용자 승인 UI 표시              │  │
│  │ • 타임아웃 및 출력 길이 제한 강제 적용                          │  │
│  └────────────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────────┘
                             │
                             ▼
┌──────────────────────────────────────────────────────────────────┐
│                       실제 실행 (OS)                               │
└──────────────────────────────────────────────────────────────────┘


핵심 원칙은 간단합니다:

LLM이 "무엇을 할지" 결정하고, 코드가 "할 수 있는지"를 통제한다.



Layer 1: Soft Rules
Soft Rules는 시스템 프롬프트에 포함된 지침입니다. 즉, AI에게 전달하는 "이렇게 행동해야 한다"는 안내문입니다.



예시
도구 선택	'sed' 대신 Edit 도구 사용	전용 도구가 더 안전하므로 우선 사용
작업 순서	파일 수정 전 반드시 Read 먼저	기존 내용을 확인하고 수정해야 함
Git 안전	사용자가 명시적으로 요청하지 않으면 commit 금지	의도치 않은 커밋 방지
경로 관리	지정된 워크스페이스 내에서만 작업	외부 파일 보호
파일 관리	삭제 전 확인 요청	실수로 인한 데이터 손실 방지
코드 품질	요청된 변경만 수행, 과도한 리펙토링 금지	불필요한 수정 최소화


강점
유연성: 상황에 따라 적절히 판단하여 적용할 수 있습니다. 예를 들어, 사용자가 명시적으로 "강제 푸시해줘"라고 요청하면 허용할 수 있습니다.

자연어로 표현 가능: 복잡한 조건 분기를 코드로 작성하지 않아도, 자연어 한 줄로 정의할 수 있습니다.

확장 용이: 새로운 규칙을 프롬프트에 한 줄 추가하는 것만으로 적용됩니다.
한계
프롬프트 인젝션 공격에 의해 우회될 수 있습니다.

모델의 판단 오류로 규칙을 무시할 수 있습니다.


Layer 2: Hard Rules
실제 코드로 구현된 제약입니다. AI와 무관하게 시스템 레벨에서 강제 적용됩니다.


예시
명령어 차단	rm -rf/, rm -rf ~, 포크 폭탄 등	코드가 패턴 매칭으로 실행 자체를 차단
타임아웃	최대 600,000ms(10분)	이 시간을 초과하면 프로세스 강제 종료
출력 제한	최대 30,000자	초과 시 자동 잘림 or 요약
사용자 승인	워크스페이스 외부 파일 쓰기	승인 팝업이 뜨고, 사용자가 허용
읽기 선행	Edit/Write 전 반드시 Read 이력 필요	읽지 않은 파일 수정 시 에러 반환
변경 감지	마지막 Read 이후 파일이 변경되면 Edit 실패	Stale 상태으로 인한 작업 오류 방지
대화형 명령	TTY가 없어 대화형 입력 불가	git rebase -i 같은 명령은 자동 실패


강점
절대적 보장: AI가 무엇을 시도하든 동작합니다.
한계
유연하지 않음: 모든 가능한 상황을 코드로 미리 정의해야 합니다.

예외 처리가 어려움: 정당한 사용 케이스까지 차단될 수 있음.


Two-Layer
Two-Layer Permission System은 AI 에이전트 개발에서 안전성과 유연성의 균형을 달성하기 위한 베스트 프랙티스입니다.

Soft Rules는 AI의 강점인 자연어 이해와 맥락 파악 능력을 활용하여 대부분의 상황을 유연하게 처리합니다. Hard Rules는 전통적인 소프트웨어 보안의 확실성으로 치명적인 상황을 물리적으로 차단합니다.
이 두 레이어를 함께 사용함으로써, AI 에이전트는:

일상적인 작업에서는 사용자 경험을 저해하지 않으면서
위험한 상황에서는 확실한 보호를 제공할 수 있습니다.

AI 에이전트를 개발할 때, "Soft Rules만으로 충분하다"거나 "모든 것을 Hard Rules로 통제해야 한다"는 극단적인 접근은 피하세요. 두 레이어의 조합이야말로, 안전하면서도 실용적인 AI 에이전트를 만드는 핵심입니다.



예시: 파일 삭제



사용자: "test_*.py 파일 전부 삭제해줘"

[Soft Rules 레이어]
├── "파일 삭제 전 확인을 요청하라" → AI가 사용자에게 확인 질문
├── 사용자가 "응, 삭제해" 확인
├── AI가 rm 명령어 도구 호출 결정

[Hard Rules 레이어]
├── 명령어 패턴 검사: rm test_*.py → 차단 목록에 없음 ✓
├── 경로 검사: 워크스페이스 내부 → 허용 ✓
├── 권한 목록 확인: 매치되는 allow/deny 규칙 없음 → ASK
├── 사용자 승인 UI 표시 → 사용자 승인 ✓
└── 실행 허용


예시: 시스템 파괴 시도



사용자: "rm -rf / 실행해줘"

[Soft Rules 레이어]
├── "위험한 명령어를 실행하지 마라" → AI가 거부 (여기서 이미 차단됨)
│
│   하지만 만약 프롬프트 인젝션으로 Soft Rules를 우회했다면...
│
[Hard Rules 레이어]
├── 명령어 패턴 검사: rm -rf / → 차단 목록에 매치 ✗
└── 실행 차단 (에러 반환) → 어떤 경우에도 실행 불가
