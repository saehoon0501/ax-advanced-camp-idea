## 9) Dynamic Persona (동적 페르소나/모드 라우팅)

### 개발 Principle (Context Engineering 관점)
- **모드 전환은 컨텍스트 전환**: 페르소나(엄격한 리뷰어/친근한 친구/교사 등)는 스타일 문제가 아니라, **우선순위/규칙/출력 형식**이 달라지는 “운영 모드”다.
- **정책 vs 페르소나 분리**: 안전/금지/컴플라이언스 같은 정책(System)은 고정, 페르소나는 그 아래 계층에서 바꾼다. (정책을 페르소나로 덮어쓰면 위험)
- **의도 기반 라우팅(Intent Routing)**: 사용자 입력을 분류해 가장 적절한 페르소나 프롬프트를 적용한다.

### 시나리오 (실습 맥락)
- `PersonaRegistry`에 `coder`, `teacher`, `friend`용 시스템 프롬프트가 저장돼 있다.
- 목표: 사용자의 메시지 의도를 보고 적절한 페르소나를 선택해 `messages[0]`(또는 persona slot)을 교체한 후 LLM을 호출한다.

### 학습 목표
- 시스템 프롬프트 계층에서 “고정 정책”과 “가변 페르소나”를 분리하는 구조를 익힌다.
- 키워드/룰 기반 라우팅을 만들고 테스트한다.

### 요구사항 (Student Task)
`route_persona(user_message)`를 구현하라.
- **동작**
  - 키워드 기반으로 intent 판별(예: `"def"`, `"class"` → coder)
  - 선택된 persona prompt를 `messages[0]`에 반영(또는 별도 persona message 삽입)
- **반드시 만족**
  - 입력 `"def hello_world():"` → coder prompt
  - 입력 `"I'm sad."` → friend prompt

### 구현 가이드(실습 단순화)
- **키워드 예시**
  - coder: `def`, `class`, `bug`, `stack trace`, `TypeError`
  - teacher: `explain`, `teach`, `why`, `how`
  - friend: `sad`, `lonely`, `tired`, `depressed`

### 실패 모드 / 주의점
- **정책 덮어쓰기**: messages[0]이 “정책”까지 포함한다면, persona 교체로 정책이 날아갈 수 있다.  
  - 권장: `messages[0]`은 정책 고정, `messages[1]`을 persona 슬롯으로 둬 교체
- **급격한 톤 변화**: 같은 대화에서 너무 자주 persona가 바뀌면 사용자 경험이 깨진다.  
  - 권장: 히스테리시스(최근 N턴 유지), 확신 낮으면 유지
- **오분류**: 키워드만으로 intent를 완벽히 맞추기 어렵다.  
  - 권장: 폴백(teacher/default) + 사용자 확인 질문

### 테스트(제공/권장)
- **제공 테스트 아이디어**
  - coder/friend 케이스 매칭 확인
- **추가 테스트(권장)**
  - 모호한 입력(“도와줘”)은 기본 persona로
  - 복합 입력(“코드도 봐주고 위로도 해줘”) 정책 수립(우선순위/멀티 페르소나)

### 확장 과제(선택)
- **persona-별 출력 스키마**: coder는 diff/코드블록, teacher는 단계별 설명, friend는 공감+질문
- **LLM 기반 분류기**: intent 분류를 별도 작은 모델/룰+LLM 하이브리드로 개선
