## 6) State Extractor (상태 오프로딩: 구조화 메모리 추출)

### 개발 Principle (Context Engineering 관점)
- **Context Offloading**: 장기적으로 유지해야 하는 정보(이름, 선호, 목표, 제약)는 “채팅 히스토리”가 아니라 **구조화된 State**에 저장한다.
- **구조화가 곧 압축**: 텍스트를 그대로 유지하지 않고 `UserProfile.name="Alice"`처럼 **필드로 저장**하면 토큰을 줄이면서도 재사용성이 올라간다.
- **반복 최소화**: “저장 완료: 이름=..., 식단=...”을 매번 대화에 남기면 컨텍스트가 불어난다. **짧은 ACK** 또는 내부 처리 전략이 필요하다.
- **상태는 ‘근거’가 필요**: 상태를 업데이트할 때는 출처 메시지/시간을 남기면 변경/정정에 강해진다.

### 시나리오 (실습 맥락)
- `UserProfile` 클래스가 있고 필드는 `name`, `diet`를 가진다.
- 사용자 메시지 예: `"Hi, I'm John and I'm vegan."`
- 목표: 메시지에서 엔티티를 추출하여 프로필 상태로 저장하고, 대화 컨텍스트는 과도하게 키우지 않는다.

### 학습 목표
- 대화에서 핵심 정보를 **상태로 추출/정규화**하는 패턴을 익힌다.
- “대화 컨텍스트 vs 상태 저장소”의 역할 분리를 이해한다.

### 요구사항 (Student Task)
`extract_entities(last_message)`를 구현하라.
- **동작**
  - 메시지에서 이름/식단 같은 엔티티를 추출(정규식 또는 mock LLM 호출)
  - `UserProfile` 업데이트
  - (선택) 히스토리의 마지막 메시지를 짧은 ACK로 교체하거나, 다음 응답에서 짧게 확인
- **핵심 제약**
  - 컨텍스트를 불필요하게 늘리지 말 것(“반복 확인문” 금지)

### 권장 입력/출력 스키마
- **입력**
  - `last_message: str`
  - `profile: UserProfile`
- **출력(예시)**
  - `profile` 업데이트 + `ack_message: str | None`

### 구현 가이드(실습 단순화)
- **이름 추출(예시)**: `"I'm (\w+)"`, `"I am (\w+)"` 같은 패턴
- **식단 추출(예시)**: `"vegan"`, `"vegetarian"` 등 키워드 매칭

### 실패 모드 / 주의점
- **오탐/미탐**: 이름이 아이디/제품명일 수 있다. 실무에서는 사용자 확인 단계가 필요할 수 있다.
- **정정/변경 처리**: “예전엔 비건이었는데 이제 아니야” 같은 업데이트가 들어올 수 있다.  
  - 권장: 상태에 `updated_at`, `source_message_id`를 저장
- **프라이버시/컴플라이언스**: 상태 저장은 개인정보 저장과 동일하다. 5번 PII 정책과 결합해 저장 범위를 최소화해야 한다.

### 테스트(제공/권장)
- **제공 테스트 아이디어**
  - 입력 `"I am Alice."` → `UserProfile.name == "Alice"`
  - ACK가 장황하지 않아 컨텍스트가 과도하게 증가하지 않음
- **추가 테스트(권장)**
  - `"I'm Bob and I'm vegan"` 동시 추출
  - 기존 상태가 있을 때 덮어쓰기/병합 정책 검증

### 확장 과제(선택)
- **State → Prompt 주입**: 모델 호출 시 상태를 짧게 주입(예: “User: Alice, Diet: vegan”)
- **스키마 검증**: 추출 결과를 JSON Schema로 검증하고 실패 시 상태 업데이트 보류
