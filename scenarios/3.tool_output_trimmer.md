## 3) Tool Output Trimmer (툴 출력 압축/정규화)

### 개발 Principle (Context Engineering 관점)
- **Observation Compaction**: 툴 결과(Observation)는 종종 매우 장황하다. 모델이 필요한 핵심 신호만 남기고 나머지는 제거하면 **컨텍스트 예산을 추론에 재투자**할 수 있다.
- **스키마 기반 추출(Schema-driven Extraction)**: “필요한 필드 목록”을 먼저 정의하고 그 외는 버린다. 이는 재현성과 테스트 가능성을 높인다.
- **표준화된 표현(Normalization)**: 숫자/단위/시간대를 정규화하면 모델의 후속 추론이 쉬워진다.

### 시나리오 (실습 맥락)
- **상황**: `weather_tool`이 200줄 JSON(관측소, 풍향각, 습도, 원본 메타데이터 등)을 반환한다.
- **문제**: 에이전트는 실제로 **온도만 필요**하다.

### 학습 목표
- “툴 호출 → 관측값(Observation) → 모델 입력” 파이프라인에서 **관측값을 줄이는 미들웨어**를 구현한다.
- “필드 추출 + 문자열 컴팩션” 패턴을 익힌다.

### 요구사항 (Student Task)
`parse_tool_output(raw_json)` 미들웨어를 구현하라.
- **입력**: 원본 JSON 문자열 또는 dict
- **출력**: 아주 짧은 문자열(예: `"Temperature: 25C"`)
- **반드시 만족**:
  - 스키마로 정의된 필드만 사용
  - 결과 문자열 길이 제한(예: `< 50 chars`)

### 권장 스키마(예시)
- `temperature_c` (필수)
- `timestamp` (선택)
- `location` (선택)

### 실패 모드 / 주의점
- **필드 누락/키 변경**: 외부 API는 키가 바뀔 수 있다.  
  - 권장: 기본값 처리 + 오류 메시지 컴팩션(“temperature missing”)
- **단위 혼동**: C/F, m/s vs km/h 같은 단위가 섞이면 추론이 깨진다.  
  - 권장: 미들웨어에서 단위를 강제/변환
- **모델에 원본 JSON을 그대로 넣는 실수**: “편의” 때문에 원본을 넣으면 컨텍스트를 즉시 잡아먹는다.

### 테스트(제공/권장)
- **제공 테스트 아이디어**
  - 5KB mock JSON → 반환 문자열 `< 50`
  - `"25C"` 포함
- **추가 테스트(권장)**
  - 온도 값이 문자열 `"25"`로 오는 경우
  - 온도가 `null`인 경우(에러 문구 컴팩션)

### 확장 과제(선택)
- **레드랙션 결합**: 툴 출력에 PII가 섞일 수 있으면 5번 시나리오의 sanitizer를 추가 적용
- **구조적 출력**: 문자열 대신 `{"temperature_c":25}` 같은 JSON으로 정규화 후, 모델에는 짧은 문자열/표를 제공
