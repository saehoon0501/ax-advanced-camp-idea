# 4) Feature List Manager (Initializer Agent - 구조화된 기능 목록 생성)

## 개발 Principle (Context Engineering 관점)

- **구조화된 상태 관리**: "완료해야 할 기능들"을 텍스트로 나열하면 파싱 오류, 의미 모호성, 토큰 낭비가 발생한다. **JSON 같은 구조화 포맷**으로 저장하면 기계 판독이 쉽고 일관성이 높다.
- **JSON > Markdown**: Anthropic 아티클에서 강조한 핵심 인사이트 - 모델은 Markdown보다 **JSON을 수정할 가능성이 낮다**. 구조화된 포맷은 실수로 인한 손상을 방지한다.
- **테스트 기반 진행 추적**: 각 기능에 "passes: true/false" 같은 명확한 상태를 두면, "70% 완료" 같은 모호한 표현 없이 **정량적 진행도**를 추적할 수 있다.
- **불변성 원칙**: Feature list의 핵심 필드(id, description, steps)는 생성 후 변경되지 않는다. 상태 업데이트(passes, notes)만 허용된다.
- **Coding Agent의 작업 대기열**: 이 파일은 단순 TODO가 아니라, 이후 Coding Agent가 "다음 무엇을 할지" 결정하는 **우선순위 큐** 역할을 한다.

## 시나리오 (Long-Running Agent 맥락)

### 배경

Anthropic 아티클의 핵심 패턴:

> Initializer Agent가 사용자의 고수준 요구사항("Build a claude.ai clone")을 받아 **200+ 세부 기능을 구조화된 JSON 파일**로 생성한다.

```
User: "Build a blog app with posts and comments"
                    │
                    ▼
┌─────────────────────────────────────────────────────────────────┐
│  INITIALIZER AGENT                                               │
│                                                                  │
│  1. Parse high-level requirements                                │
│  2. Break down into 10-50 specific, testable features           │
│  3. Assign priority (high/medium/low)                           │
│  4. Define verification steps for each feature                   │
│  5. Save as feature_list.json                                    │
│                                                                  │
│  Output: feature_list.json (structured, parseable by Coding Agent)│
└─────────────────────────────────────────────────────────────────┘
```

### 문제

- 텍스트 기반 TODO는 파싱 어려움, 형식 변경 가능
- 진행 상태 추적이 모호함 ("거의 완료" vs "passes: true")
