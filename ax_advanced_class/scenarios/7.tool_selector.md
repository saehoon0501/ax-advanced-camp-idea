## 7) Tool Selector (동적 툴 가시성/선택)

### 개발 Principle (Context Engineering 관점)
- **Tool Overload 방지**: 도구가 많을수록 모델이 “무슨 도구를 써야 하지?”에 컨텍스트/주의력을 소모한다.  
  - 해결: **현재 과업에 필요한 도구만 노출**(system prompt/tool schema 렌더링 단계에서 필터링)
- **툴은 컨텍스트의 일부**: 도구 설명/스키마 자체가 토큰을 크게 차지하므로, “툴 선택”은 곧 “컨텍스트 예산 관리”다.
- **안전한 최소 권한(Least Privilege)**: 이메일 전송/결제/DB 삭제 같은 고위험 도구는 필요할 때만 노출해야 사고를 줄인다.

### 시나리오 (실습 맥락)
- **도구 풀**: Math, Weather, SQL, Email 등 50개 도구가 존재한다.
- **질문 예시**: `"What is 25 * 50?"`
- **문제**: 질의에 필요한 도구만 골라 system prompt에 렌더링할 수 있게 리스트를 반환한다.

### 학습 목표
- 질의 의도를 기반으로 **도구를 좁히는 라우팅 레이어**를 구현한다.
- “도구 선택”이 모델 성능/안전/비용에 미치는 영향을 이해한다.

### 요구사항 (Student Task)
`select_relevant_tools(query, all_tools)`를 구현하라.
- **출력**: `all_tools`의 부분집합(sub-list)
- **반드시 만족**
  - 계산 질의 → MathTool만 반환
  - 이메일 질의 → EmailTool만 반환
- **권장 사항**
  - 0개 또는 2개 이상 반환 정책을 명확히(예: 모호하면 2개까지 허용)

### 구현 가이드(실습 단순화)
- **키워드 기반**
  - `"calculate"`, `"*"` → MathTool
  - `"send"`, `"email"` → EmailTool
- **룰 테이블 기반**
  - intent → tools 매핑 테이블을 만들어 테스트 가능하게 유지

### 실패 모드 / 주의점
- **과소 선택(Too few)**: 필요한 도구를 빼면 모델이 엉뚱한 답을 하거나 재질문이 늘어난다.
- **과다 선택(Too many)**: 모델이 불필요한 도구를 호출하거나, 스키마 토큰이 커져 비용/품질이 악화된다.
- **고위험 도구 노출**: 필요 없는 상황에 Email/DB/Payment 도구가 노출되면 오작동 리스크가 커진다.

### 테스트(제공/권장)
- **제공 테스트 아이디어**
  - `"Calculate X"` → 반환 도구 길이 1, Math
  - `"Send email"` → 반환 도구 길이 1, Email
- **추가 테스트(권장)**
  - 모호한 질의(“도와줘”) → 0개 또는 기본 도구만
  - 복합 질의(“계산해서 이메일로 보내줘”) → Math + Email(정책 명시)

### 확장 과제(선택)
- **2단계 선택**: 1차는 룰/키워드, 2차는 소형 LLM으로 intent 분류
- **비용 기반 선택**: 고비용 도구는 confidence가 높을 때만 노출/호출
