## 8) Thought Scratcher (스크래치패드: 사고 로그와 대화 히스토리 분리)

### 개발 Principle (Context Engineering 관점)
- **사고(Reasoning)와 기록(History)의 분리**: 모델이 문제를 풀기 위해 길게 “생각”하더라도, 그 텍스트를 매 턴 대화 기록에 남기면 컨텍스트가 오염되고 비용이 증가한다.
- **Scratchpad 패턴**:  
  - 모델 출력: `THOUGHT`(내부 추론) + `ANSWER`(사용자에게 보여줄 결과)  
  - 저장: `THOUGHT`는 디버그로만 보관(또는 폐기), `ANSWER`만 대화 히스토리에 저장
- **안전/프라이버시**: 추론 텍스트에는 민감한 정보가 섞일 수 있으므로, 기본은 **저장 최소화**가 안전하다.

### 시나리오 (실습 맥락)
- 에이전트 루프에서 모델이 아래처럼 출력한다고 가정한다:
  - `THOUGHT: ...`
  - `ANSWER: ...`
- 목표: 대화 히스토리에는 `ANSWER`만 누적하고, `THOUGHT`는 별도 처리한다.

### 학습 목표
- 출력 파싱을 통해 “대화에 남길 것/남기지 않을 것”을 통제한다.
- 컨텍스트 예산 관리 관점에서 Scratchpad의 효과를 정량적으로 테스트한다.

### 요구사항 (Student Task)
`finalize_turn(model_output)`을 구현하라.
- **동작**
  - `model_output`에서 THOUGHT와 ANSWER 섹션을 파싱
  - THOUGHT는 디버그 파일에 기록하거나 폐기
  - messages에는 ANSWER만 append
- **반드시 만족**
  - THOUGHT 500단어가 있어도, messages는 ANSWER 길이만큼만 증가

### 입력/출력 스키마(권장)
- **입력**
  - `model_output: str`
  - `messages: List[Message]`
- **출력**
  - `messages` 업데이트(ANSWER만)
  - `debug_thought: str | None`

### 실패 모드 / 주의점
- **포맷 불일치**: 모델이 `THOUGHT:`를 빼먹거나 순서를 바꿀 수 있다.  
  - 권장: 파서에 “없으면 전체를 ANSWER로 처리” 같은 폴백
- **THOUGHT에 중요한 사실이 들어감**: 저장을 버리면 디버깅이 어려울 수 있다.  
  - 권장: 기본은 폐기, 필요 시 샘플링/에러 시에만 저장
- **로그 보안**: THOUGHT 로그 파일은 운영에서 민감 데이터가 될 수 있다(접근 통제 필요).

### 테스트(제공/권장)
- **제공 테스트 아이디어**
  - 500단어 Thinking + 짧은 Answer → messages 증가량이 Answer만큼인지 확인
- **추가 테스트(권장)**
  - THOUGHT만 있고 ANSWER가 없는 경우
  - ANSWER만 있는 경우

### 확장 과제(선택)
- **Structured output**: `{"thought":"...","answer":"..."}` JSON으로 출력하도록 하고 JSON 파싱
- **Thought 압축 저장**: THOUGHT를 원문 저장하지 않고, 짧은 메타(토큰 수, 실행한 도구, 실패 이유)만 남기기
